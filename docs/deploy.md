# Deploy runbook

Manual checklist for standing up production. These are dashboard steps across five services (Atlas, Stripe, Cloudflare, Render, UptimeRobot) — nothing here is automated, and it's meant to be run by hand, once, by whoever owns those accounts.

Two steps exist only because of v2 and are easy to miss: the **second webhook event** in step 2.2, without which unpaid orders pile up forever, and the **one-shot order migration** in step 6.

## 1. MongoDB Atlas

1. Create a free **M0** cluster.
2. Create a database user (username + password) scoped to that cluster.
3. Under Network Access, allow `0.0.0.0/0` (Render's egress IPs aren't static on the free plan).
4. Copy the SRV connection string (`mongodb+srv://...`) — this becomes Render's `MONGO_URL`.

## 2. Stripe (test mode first)

1. In the Stripe dashboard (test mode), copy the secret key (`sk_test_...`).
2. Create a webhook endpoint pointing at `https://api.shop.augustoamaral.com/api/stripe/webhook`, subscribed to **both** of these events:

   | Event | What the API does with it |
   |---|---|
   | `checkout.session.completed` | Confirms the order: `pending → paid`, records what Stripe actually charged, then decrements stock (a lost race sets `oversold`). |
   | `checkout.session.expired` | Moves a lapsed order `pending → expired`. |

   **Both, not just the first.** v2 creates the order *before* the redirect to Stripe, so an abandoned checkout is a real `pending` document sitting in Mongo — and `checkout.session.expired` is the only thing that ever clears it. Nothing else in the API can: the admin panel has no transition out of `pending`, and the boot-time sweep only touches orders that never got a Stripe session id at all. Subscribe to `completed` alone and pending orders accumulate forever, silently, with nothing anywhere reporting an error.

   Those two are also the complete list: `apps/api/src/routes/webhook.ts` verifies the signature and then ignores every other event type, so subscribing to more costs nothing and achieves nothing.
3. Copy the webhook's signing secret (`whsec_...`) — both values go into Render (`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`).
4. **Turn on e-mail receipts for successful payments.** Stripe's receipt is the buyer's only confirmation e-mail: this shop has no transactional e-mail provider, and tracking codes are sent by hand later from the admin panel's prefilled `mailto:` link. The Checkout Session is created with `customer_email` set to the address the buyer typed into the checkout form, so Stripe has somewhere to send it.

   *Unverified from this repo:* the exact location of that setting in the Stripe dashboard (it is under the customer-email settings) and whether test mode and live mode keep it separately — assume they do, and check it again at go-live, the same way the webhook endpoint has to be created twice.

## 3. Cloudflare R2

1. Enable R2 on the Cloudflare account (requires a payment card on file, even though usage stays within the free tier).
2. Create a bucket named `handmade-portfolio`.
3. Add a custom public domain to the bucket: `img.shop.augustoamaral.com`.
4. Create an R2 API token and copy the access key ID / secret access key into `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY`.

## 4. Render

1. New → Blueprint, point it at this repo (`render.yaml` at the root defines the `handmade-portfolio-api` service).
2. Fill in the env vars marked `sync: false` in the Render dashboard: `MONGO_URL` (from step 1), `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` (from step 2), `ADMIN_EMAIL`, `ADMIN_PASSWORD_HASH`, `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` (from step 3). `JWT_SECRET` is auto-generated by Render; `WEB_ORIGIN`, `R2_BUCKET`, `R2_PUBLIC_URL` are already set as literal values in `render.yaml`.

   Those eight plus those four are exactly what `apps/api/src/env.ts` validates, checked against the schema: **v2 added no environment variable and dropped none.** The only entry in the schema that `render.yaml` does not carry is `PORT`, which Render sets itself and which the schema defaults to 3001.
3. Generate `ADMIN_PASSWORD_HASH` locally before pasting it in:
   ```bash
   node -e "console.log(require('bcryptjs').hashSync(process.argv[1], 10))" 'the-password'
   ```
4. Add a custom domain `api.shop.augustoamaral.com` to the Render service, then create the matching CNAME in Cloudflare DNS. Set the record to **DNS-only (grey cloud)** — Render's docs require this so their own TLS/proxying isn't double-wrapped by Cloudflare's proxy.

## 5. Cloudflare Workers Builds

1. Connect this repo in the Cloudflare dashboard (Workers & Pages → Workers Builds).
2. Build command:
   ```
   npm ci && npm run build -w @shop/shared && VITE_API_URL=https://api.shop.augustoamaral.com npm run build -w @shop/web
   ```
   `VITE_API_URL` is not optional in production: `apps/web/src/app/api/client.ts` falls back to `http://localhost:3001` when it is unset, so a build without it produces a storefront that talks to nothing.
3. Deploy command: `npx wrangler deploy` (uses `wrangler.jsonc` at the repo root, which serves `apps/web/dist` as static assets with SPA fallback routing).
4. Add the custom domain `shop.augustoamaral.com` to the Worker.

## 6. Migrate the v1 orders (first v2 deploy only)

v2 renamed and reshaped the order document. One script does the whole conversion:

```bash
MONGO_URL='<atlas-srv-string>' npm run migrate:v2 -w @shop/api
```

**When:** once, as soon as the first v2 API deploy is live (steps 4 and 5), and **before the shop takes its first v2 order.** The order numbers it backfills come from the same atomic counter live checkouts draw from, and it numbers the old orders oldest-first — so a purchase that lands before the migration runs takes `#MHP-0001` and pushes every older order behind it.

**What it does**, to every order document that has no `orderNumber` yet, oldest `createdAt` first:

- assigns an `orderNumber` from the shared counter;
- rewrites `fulfilled` as `shipped` (the other v1 statuses keep their names);
- turns `customer { name, email }` into `buyer { name, email }` and drops `customer`;
- converts v1's Stripe-shaped `shippingAddress` into the v2 shape, and infers `shippingMethod` from the country — `BR → pac`, anything else → `intl` — because v1 stored no method and had exactly two flat rates;
- sets `locale: 'en'`, `paidAt` from `createdAt`, and `shippedAt` from `updatedAt` on shipped orders.

**What it needs:** `MONGO_URL` and nothing else. Unlike the seed in step 7, this script reads `process.env.MONGO_URL` directly instead of going through `getEnv()`, so it never touches the rest of the schema. Measured by running it with nothing else in the environment.

**If it is run twice:** nothing happens. It only selects documents that have no `orderNumber`, so a second run prints `migrated 0 v1 order(s)` and leaves every document — and the counter — exactly as the first run left them. Measured, not assumed: re-run it without worrying if you are not sure the first one finished.

**No manual index work is needed.** v1 left a non-sparse unique index on `stripeSessionId` that v2 needs to be sparse; the API runs `Order.syncIndexes()` on every boot (and the migration runs it again at the end), so the deploy itself rebuilds it.

On a genuinely empty database this step is a no-op and can be skipped.

## 7. Seed the product catalogue

Once Atlas and Render's env vars are in place, seed from a machine with the env vars available:

```bash
MONGO_URL='<atlas-srv-string>' npm run seed -w @shop/api
```

The seed only ever *reads* `MONGO_URL`, but it gets it through `getEnv()`, which parses the entire environment schema the first time it is called — so without every variable present the script dies on a ZodError before it connects. They do **not** have to be the real production values, though: nothing else is read, so the placeholders in `apps/api/.env.example` are enough as long as the URL-shaped and e-mail-shaped ones parse. Measured: the seed completes with `.env.example`'s values verbatim and a real `MONGO_URL`.

**⚠️ It inserts; it never updates.** Every product is written with `updateOne({ slug }, { $setOnInsert: … }, { upsert: true })`, so a slug that already exists is left completely alone — and all four v2 slugs are the same four v1 shipped. On the live database that means **the v2 product fields are not backfilled**: the existing four products get no `subtitle`, no `specs` and no `featured` flag. Measured against a v1-shaped document, not assumed.

Nothing breaks — the API defaults all three when it reads a document — but two things are visibly wrong until the content is filled in:

- product pages show no subtitle and no ficha técnica;
- the home page's hero uses the first active `featured` product and falls back to the first active product when there is none, so it will show whichever product is oldest instead of the handwritten letter.

Fix it through `/admin/products` after the deploy — that is what the panel is for — or update the four documents by hand. On an empty database none of this applies: the seed inserts all four with their full v2 content.

## 8. UptimeRobot

Create an HTTP(S) monitor on `https://api.shop.augustoamaral.com/api/health`, checked every 5 minutes. This also keeps Render's free-tier instance from idling.

## 9. Verify a test-mode purchase end to end

With Stripe still in test mode, do a full purchase on the live site using the test card `4242 4242 4242 4242` (any future expiry, any CVC). v2 splits a purchase across two moments, so check both:

1. **Before paying.** The order already exists: it shows in `/admin/orders` with status `pending` (the default filter includes it), and `/thanks?order=…&session_id=…` renders it and polls for about 30 seconds waiting for the payment.
2. **After paying.** `checkout.session.completed` arrives, the order flips to `paid`, the purchased product's stock is decremented, and the `/thanks` page updates itself without a reload. Stripe's receipt should land in the buyer's inbox (step 2.4). The Stripe dashboard should also show the buyer's address on the PaymentIntent — v2 sends it as `payment_intent_data.shipping` rather than collecting it on Stripe's page, and postage appears as an ordinary line item rather than a shipping option.
3. **The expire path**, which is the half nobody thinks to test and the whole reason step 2.2 has two events in it. Start a second checkout and abandon it on Stripe's page. When Stripe expires the session, the order should move to `expired` and show up under `/admin/orders?status=expired` — the default filter hides it, so looking at the default list proves nothing either way.

   *Unverified from this repo:* how long Stripe leaves an unpaid Checkout Session open before expiring it, and whether the dashboard offers a way to expire one on demand. Both are Stripe's behaviour, not this application's. If you would rather not wait, Stripe's API can expire a session directly — the checkout route already calls `stripe.checkout.sessions.expire` on one of its own error paths.

## 10. Go-live (later, after Stripe KYC)

Once Stripe finishes account activation (KYC), swap `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` in Render to their live-mode values (`sk_live_...` / a webhook endpoint created against the live API). Stripe's test and live webhook endpoints are separate objects, so **the live endpoint needs both events from step 2.2 subscribed again** — `checkout.session.completed` *and* `checkout.session.expired`. The receipt setting from step 2.4 is very likely per-mode too; confirm it rather than assuming it carried over. Nothing else in this runbook changes — same Render service, same Cloudflare Worker, same domains, same database, and no second migration.

While the Stripe account is still under review, live keys already work for creating Checkout Sessions but payments stay paused, so a real card fails at the payment step. Wait for the activation email, then do one real purchase of the cheapest item and refund it from the Stripe dashboard to verify the webhook end to end.
