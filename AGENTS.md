# My Handmade Portfolio

A working e-commerce store selling the author's own handmade work (handwritten letters, drawings, doodles) with a real Stripe Checkout integration — not a demo, real payments. Monorepo: `apps/api` (Express + Mongoose), `apps/web` (React + Vite), `packages/shared` (types/zod schemas/constants), `e2e` (Playwright). Run tests with `npm test` (runs `@shop/shared`, `@shop/api`, `@shop/web` suites in sequence); `npm run e2e` for Playwright.

## Gotchas

- **`packages/shared` is consumed via its built `dist`, not source.** Its `exports` field points to `./dist/index.js`. Editing `packages/shared/src/*.ts` and running `npm test` leaves `apps/web` and `apps/api` testing against the stale build — the suite goes green while actually exercising old values (measured 2026-09-10 by changing a constant: `shared`'s own suite went red as expected, but `web`'s stayed green because it read the old `dist`). This is especially costly for mutation testing, where it disguises itself as "the assertion is inert" instead of "the app never saw the new code." After any edit to `packages/shared/src`, run `npm run build -w @shop/shared` before trusting any `apps/web`/`apps/api` test result. CI is unaffected — `.github/workflows/ci.yml` already runs that build before `npm test`.
- **The vitest fork-pool cap only works at a config's root `test:` block — inside a `projects: []` entry it's silently ignored.** `apps/web/vitest.config.ts` is the correct, live reference: `maxWorkers: 2`, `minWorkers: 1`, and `poolOptions.forks.{minForks: 1, maxForks: 2}` sit above its `unit` and `storybook` projects, with an inline comment explaining why. Vitest builds one worker pool per run from the root config's `poolOptions.forks` (`createForksPool`, vitest 3.2.7) and never reads a project's; a project's `poolOptions.forks` only accepts `singleFork`/`isolate` anyway (no `maxForks`), yet setting it there still passes typecheck and gets echoed back by that project's *resolved* config — so it looks live when it's actually dead. `apps/api` and `packages/shared` have no `projects` array, so they pass the same cap as CLI flags on their `test` scripts instead (`vitest run --pool=forks --poolOptions.forks.minForks=1 --poolOptions.forks.maxForks=2`); `apps/web`'s `test` script is plain `vitest run`, relying entirely on the config file. To check any config's cap is really active, read its resolved output, not the source file: `node --input-type=module -e "import {createVitest} from 'vitest/node'; const v=await createVitest('test',{watch:false}); console.log(v.config.maxWorkers, JSON.stringify(v.config.poolOptions)); await v.close()"` — `poolOptions` coming back as `{"threads":{},"forks":{}}` means it's inert and Node's `numCpus - 1` fallback is running instead.
- **On Node 25+, jsdom's `localStorage`/`sessionStorage` need a manual shim in test setup — don't remove it as dead code.** Node's own global Web Storage shadows jsdom's inside vitest's jsdom test environment (`globalThis === window` there, and the `localStorage` property already resolves to Node's own inert accessor rather than ever installing jsdom's `Storage`), so `localStorage.setItem` throws `TypeError: Cannot read properties of undefined`. A "simpler" fix like `globalThis.localStorage = window.localStorage` is a no-op — both sides are already `undefined`, there's no jsdom storage anywhere to copy from. The actual fix, already in place in `apps/web/test/setup.ts` (commit `211c835`, 2026-09-09): install a small `Map`-backed `MemoryStorage` behind a capability guard (`if (typeof globalThis[key]?.setItem !== 'function')`), for both `localStorage` and `sessionStorage`. The guard is capability-based rather than Node-version-based specifically so CI (pinned to Node 22 in `.github/workflows/ci.yml`) keeps using jsdom's real `Storage` untouched. Don't declare the class `implements Storage` — the DOM interface's string index signature isn't satisfiable by a plain class.
- **An isolated, non-reproducible failure in the `@shop/api` suite on a Node-25+ dev machine is a candidate for a local environment artifact before it's a candidate for a real bug (open hypothesis, 2026-09-10, unconfirmed).** During PR 5 of webshop v2, the full root `npm test` run (which runs the three workspaces in series) failed twice, in different `supertest`-based tests, on a Mac running Node v26.2.0 — neither ever reproduced on rerun, and the same tests never failed running `-w @shop/api` alone or in CI (pinned to Node 22). Mock leakage, cross-workspace races, and a missing fork-pool guardrail were checked and ruled out, not just assumed away. Don't rewrite the test on the first such failure: capture the full error text (a prior failure's specifics were lost because only summary lines were grepped) and rerun. If the same failure ever reproduces in CI, this hypothesis is wrong and it's a real bug.
